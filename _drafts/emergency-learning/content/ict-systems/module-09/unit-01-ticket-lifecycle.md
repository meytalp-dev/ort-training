# יחידה 1 — תהליך ניהול תקלה

> רעיון מרכזי אחד (מנה אחת): תקלה מתקדמת בשלבים, מהפנייה ועד הסגירה. [מקור: תפעול מערכות תקשוב · מ9]

רלוונטיות לקהל מגוון: תהליך מסודר מסייע בשירות, בניהול ובחיי היום־יום.

## 🟢 basic (אני איתך)

### פתיח

משתמשת מדווחת שאינה מצליחה להתחבר למערכת.

נפתח טיקט חדש עבור התקלה. [מקור: תפעול מערכות תקשוב · מ9]

### הסבר

תהליך ניהול תקלה כולל חמישה שלבים:

1. קבלת הפנייה.
2. סיווג ותיעדוף.
3. טיפול בתקלה.
4. עדכון המשתמש.
5. סגירה ותיעוד.

[מקור: תפעול מערכות תקשוב · מ9]

### דוגמה

בכרטיס המשתמש נכתב: "הסיסמה אינה מתקבלת".

הפנייה מתקבלת, מסווגת ומטופלת.

המשתמש מקבל עדכון.

הפתרון מתועד, והטיקט נסגר. [מקור: תפעול מערכות תקשוב · מ9]

### שאלה 1 — סידור שלבים

סדרו את הכרטיסים לפי התהליך:

- סגירה ותיעוד
- טיפול בתקלה
- קבלת הפנייה
- עדכון המשתמש
- סיווג ותיעדוף

✅ קבלה → סיווג → טיפול → עדכון → סגירה.

💡 התחילו מהאירוע שיוצר את הטיקט.

### שאלה 2 — שלב חסר

לוג המערכת מציג:

קבלה → סיווג → טיפול → סגירה.

איזה שלב חסר?

א. עדכון המשתמש

ב. פתיחת תקלה נוספת  
`error_type: overgeneralization`

ג. מחיקת פרטי הפנייה  
`error_type: rule-application`

✅ תשובה: עדכון המשתמש. [מקור: תפעול מערכות תקשוב · מ9]

💡 לפני הסגירה, משתפים את המשתמש בתוצאה.

### סיכום

תקלה עוברת חמישה שלבים.

מתחילים בפנייה ומסיימים בתיעוד וסגירה. [מקור: תפעול מערכות תקשוב · מ9]

## 🔵 standard (מנסה לבד)

### פתיח

בלוג המערכת מופיעים שלבים בסדר מבולבל.

המטרה היא לשחזר את מסלול הטיפול.

### הסבר

כל שלב מכין את השלב הבא.

קבלת הפנייה מספקת מידע ראשוני.

הסיווג והתיעדוף מכוונים את הטיפול.

לאחר הטיפול, מעדכנים וסוגרים. [מקור: תפעול מערכות תקשוב · מ9]

### דוגמה

כרטיס משתמש:

"עמדת הקבלה אינה מדפיסה הזמנות".

לוג הטיקט:

- התקלה סווגה.
- המשתמש קיבל עדכון.
- הפנייה התקבלה.
- הפתרון תועד.
- התקלה טופלה.

### שאלה 1 — בניית רצף

כתבו מספר מאחת עד חמש:

- המשתמש קיבל הודעת פתרון.
- התקלה נבדקה וטופלה.
- הפנייה נרשמה.
- הפתרון תועד והטיקט נסגר.
- התקלה סווגה ותועדפה.

✅ סדר נכון: 4, 3, 1, 5, 2.

💡 חפשו מה חייב להתרחש לפני הטיפול.

### שאלה 2 — איתור שיבוש

איזה רצף אינו תקין?

א. פנייה → סיווג → טיפול → עדכון → סגירה

ב. פנייה → טיפול → סיווג → עדכון → סגירה  
`error_type: rule-application`

ג. סיווג → פנייה → טיפול → עדכון → סגירה  
`error_type: form-confusion`

✅ תשובה: רצפים ב׳ וג׳. [מקור: תפעול מערכות תקשוב · מ9]

💡 סיווג מגיע אחרי הפנייה ולפני הטיפול.

### שאלה 3 — השלמת לוג

השלימו שני שלבים:

קבלה → ______ → טיפול → ______ → סגירה.

✅ תשובה: סיווג ותיעדוף; עדכון המשתמש.

💡 בדקו מה קורה סביב הטיפול.

### סיכום

סדר השלבים מציג את מצב הטיקט.

לוג מסודר מראה מה בוצע ומה נשאר. [מקור: תפעול מערכות תקשוב · מ9]

## 🟣 advanced (בא לי אתגר)

### פתיח

טיקט נסגר, אך המשתמש לא קיבל פתרון.

צריך לנתח את לוג המערכת.

### הסבר

רצף שלבים אינו רק רשימת פעולות.

כל שלב צריך להופיע בזמן המתאים.

דילוג על שלב יוצר פער בתהליך. [מקור: תפעול מערכות תקשוב · מ9]

### דוגמה

לוג מערכת:

09:05 — התקבלה פנייה.

09:12 — התקלה סווגה.

09:40 — הטיקט נסגר.

10:15 — המשתמש ביקש עדכון.

בלוג חסרים טיפול ועדכון משתמש. [מקור: תפעול מערכות תקשוב · מ9]

### שאלה 1 — ניתוח לוג

סמנו אילו שלבים חסרים:

- קבלת פנייה
- סיווג ותיעדוף
- טיפול בתקלה
- עדכון המשתמש
- סגירה ותיעוד

✅ חסרים טיפול ועדכון המשתמש.

💡 השוו בין הלוג לחמשת השלבים.

### שאלה 2 — יצירת לוג מתוקן

כתבו לוג מתוקן בחמש שורות.

הוסיפו שעה מתאימה לכל שלב.

✅ הלוג צריך לכלול את כל השלבים.

💡 ודאו שהסגירה מופיעה אחרונה.

### שאלה 3 — בחירת תיקון

איזה תיקון מתאים ביותר?

א. לפתוח טיקט נוסף ולמחוק את הקודם  
`error_type: overgeneralization`

ב. להוסיף טיפול ועדכון לפני הסגירה

ג. להשאיר את הלוג ללא שינוי  
`error_type: attention`

ד. להעביר את הסיווג לאחר הסגירה  
`error_type: concept`

✅ תשובה: להוסיף טיפול ועדכון לפני הסגירה.

💡 תיקון טוב משחזר את סדר התהליך.

### סיכום

לוג תקין משקף את מחזור הטיקט.

כל שלב מופיע בסדר ברור ומתועד. [מקור: תפעול מערכות תקשוב · מ9]

### הערת אימות

היחידה נכתבה מרשימת הכשירויות שסופקה.

נדרש אימות פדגוגי של רכז המגמה.

יש לבדוק התאמה למערכת הטיקטים הנלמדת.
