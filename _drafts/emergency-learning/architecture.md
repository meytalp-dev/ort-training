## 0. מה המסמך הזה נותן למפתח

זה מסמך ההנדסה של **שני המנגנונים שמפעילים את כל המערכת**:

1. **מנגנון המצבים** — איך בית ספר עובר בין שגרה / מרחוק / חירום, מי מורשה להחליף, ומה קורה טכנית ברגע ההחלפה בכל שמונת העולמות.
2. **מנגנון הכניסה** — שתי שכבות: שכבת קשר בקישור אישי בלי סיסמה (magic link), ושכבת למידה עם הרשמה קלה. כולל כל תרחישי הקצה של טלפונים משותפים, מספר שהתחלף, ואובדן מכשיר.

**הבטחת המסמך:** מפתח יכול לממש את המתג ואת הכניסה **מהמסמך הזה בלבד**, בלי להמציא כללים. כל תרחיש קצה סגור כאן במפורש.

**עוגן במודל הנתונים:** המסמך נשען על הישויות שכבר הוגדרו ב-`data-model.md` — `SystemMode` (§2.8), `Student.access_token` / `Student.registered` (§2.1), `StaffMember.access_token` (§2.3), `CheckIn` (§2.7), `Notification` (§2.10). מקומות שבהם נדרש שדה חדש שאינו קיים עדיין במודל מסומנים במפורש ✎ ומרוכזים ב-§10.

# חלק א — מנגנון המצבים

## 1. שלושת המצבים ומקור האמת

```
routine   ── "בונים את ההרגל"        ── ברירת המחדל
remote    ── "יום מקוון מתוכנן"       ── מתוכנן מראש (scheduled_for)
emergency ── "קשר לפני תוכן"          ── מיידי
```

**מקור האמת למצב הנוכחי של בית ספר = רשומת ה-`SystemMode` האחרונה שלו** (`ORDER BY activated_at DESC LIMIT 1`, לפי `school_id`). אין שדה "מצב נוכחי" נפרד על `School` — זה היה מייצר מקור אמת כפול. המצב הוא תמיד תוצאה של השאילתה על יומן המצבים.

**כל אירוע מטביע את המצב שלו בזמן היצירה.** בעת יצירת `CheckIn` / `Assignment` / `ContactLog` / `Notification`, השדה `mode` **מוטבע** מהמצב הנוכחי של בית הספר. מעבר מצב **לא** מעדכן אירועים קיימים — היסטוריה נשמרת נאמנה, ומשימה שנשלחה בשגרה נשארת "שגרה" גם אחרי שעברנו לחירום.

## 2. מה משתנה בכל עולם בכל מצב (טבלת עולם × מצב)

זו הטבלה המחייבת. כל תא = ההתנהגות בפועל של אותו עולם באותו מצב. המפתח מממש את ההבדלים כ**קונפיגורציה נגזרת מ-`mode`**, לא כשלושה מסכים שונים.

| עולם | routine (שגרה) | remote (מרחוק) | emergency (חירום) |
|------|----------------|-----------------|---------------------|
| **תלמיד — check-in** | `type=presence` ("אני כאן"), קליל, פותח יום/שיעור | `type=presence`, פותח את יום הלמידה בבוקר | `type=emotional` ("איך אתה היום?", 4 מצבי רוח), `is_sensitive=true` — **לב המערכת** |
| **תלמיד — משימות** | 1–2 לשבוע למקצוע | 3–5 ליום מתוכנן, כל אחת צעד 10 דק' | צעד אחד ליום, **רשות** ("המורה ראה" במשקל כפול) |
| **תלמיד — הערכה** | מופעי הערכה עם ציון כחלק מהתרגול | אופציונלי | זמין אך **רשות בלבד**, בלי לחץ |
| **תלמיד — "המורה ראה"** | חיווי רגיל | חיווי רגיל | משקל רגשי מוגבר — הטקסט מדגיש מי ומתי |
| **מחנך — לוח דופק** | הרגלי שימוש, הצצה 1–2 בשבוע | לוח נוכחות יומי (התחיל/סיים/לא נראה) | מרכז העולם — דופק רגשי + **חובת פנייה לאדום תוך 24ש'** |
| **מחנך — דגלים רגשיים** | כבויים (אין check-in רגשי) | כבויים | **פעילים** — `distress_flag` מדליק `FlagEvent` |
| **מורה מקצועי** | שולח מהמדף כשיעורי בית | מתזמן משימות מראש ליום (`scheduled_for`) | שולח רק יחידות מתויגות "מתאים לחירום" — קצרות, מרגיעות |
| **מנהל — דוח** | שבועי, מדדי אימוץ | יומי, אחוז השתתפות לפי שכבה | **יומי לוואטסאפ 19:00** — 3 מספרים + רשימת אדומים בראש |
| **מנהל — דופק צוות** | תצוגה רגילה | תצוגה רגילה | מודגש — "גם מורים בחירום", מורה שלא נכנס יומיים בולט |
| **פיקוח** | תמונת אימוץ מצרפית | תמונת השתתפות מצרפית | **תמונת חירום ארצית** — כמה בי"ס בחירום, כמה נראו ברמת המדינה |
| **הורים** | הודעה שבועית אחת | התראה יום קודם ("מחר יום מהבית") | עדכון קצר ומרגיע בכל מעבר מצב |
| **AI (כפתור)** | זמין בכל עולם | זמין | זמין — ללא שינוי במגבלות הבטיחות |
| **טון כללי** | רגוע, הרגלי | ענייני, מאורגן | חם, אנושי, מינימלי |

> **עיקרון מימוש:** ההבדלים בין המצבים הם **נתונים** (`MODE_CONFIG[mode]`), לא קוד מסועף. כל מסך קורא את המצב הנוכחי פעם אחת, טוען את הקונפיג המתאים, ומצייר. כך מעבר מצב = החלפת אובייקט קונפיג + רה-רנדר, לא טעינת אפליקציה אחרת.

### 2.1 סכמת קונפיג המצב (לצד הלקוח)

```js
const MODE_CONFIG = {
  routine: {
    checkinType: "presence",        // presence | emotional
    emotionalCheckin: false,
    tasksPerDay: 2,                 // רמז לתצוגה, לא אכיפה קשיחה
    tasksRequired: false,
    flagsActive: false,             // דגלים רגשיים כבויים
    principalReport: "weekly",
    accentColor: "--mode-routine",  // ירוק רך (design-system)
    tone: "habitual"
  },
  remote: {
    checkinType: "presence",
    emotionalCheckin: false,
    tasksPerDay: 4,
    tasksRequired: false,
    flagsActive: false,
    principalReport: "daily",
    accentColor: "--mode-remote",   // תכלת
    tone: "organized"
  },
  emergency: {
    checkinType: "emotional",
    emotionalCheckin: true,
    tasksPerDay: 1,
    tasksRequired: false,
    flagsActive: true,              // דגלים רגשיים פעילים
    principalReport: "daily_1900_whatsapp",
    accentColor: "--mode-emergency",// כתום חם #E8722C (לא אדום — עדיין לאישור מיטל, T0.3)
    tone: "warm_minimal"
  }
};
```

> הקונפיג הזה הוא **מקור האמת היחיד להבדלי המצבים בצד הלקוח**. שרת ולקוח חולקים אותו (JSON משותף). הוספת התנהגות תלוית-מצב = הוספת שדה לקונפיג, לא `if (mode === ...)` מפוזר.

## 3. מי מחליף מצב — הרשאות ותיעוד

מעבר מצב הוא ההחלטה הכי כבדה במערכת. שתי רמות הרשאה, עם גובר ברור:

| רמה | מי | היקף | גובר? |
|-----|-----|------|--------|
| **בית ספר** | מנהל (`StaffRole.role=principal`, בהיקף `school_id` שלו) | בית הספר שלו בלבד | לא — נכנע להנחיה ארצית |
| **ארצי** | פיקוח (`StaffRole.role=supervisor`, `school_id=null`) | קבוצת בתי ספר / מחוז / כלל המערכת | **כן — גובר על החלטת מנהל** |

**כלל הגובר (override):** אם קיימת הפעלה ארצית פעילה (`SystemMode` עם `activated_by=null` + `note` שמסמן מקור ארצי) על בית ספר — המנהל **לא יכול להוריד** את בית הספר מתחת למצב שהפיקוח הכריז. הוא יכול רק להעלות חומרה (למשל הפיקוח הכריז `remote` ארצי; מנהל מקומי רשאי להעלות ל-`emergency` בגלל אירוע מקומי). **הורדה** ממצב ארצי חסומה בצד השרת עד שההפעלה הארצית מבוטלת.

**החלפה = אירוע מתועד.** כל מעבר יוצר רשומת `SystemMode` חדשה (append-only, אף פעם לא UPDATE). התיעוד המחייב:

```
SystemMode {
  id, school_id,
  mode:          "routine|remote|emergency",   // המצב החדש
  activated_by:  staff_id | null,              // null = הפעלה ארצית
  scheduled_for: date | null,                  // null = מיידי (remote יכול להיות עתידי)
  note:          string,                        // ✎ חובה: סיבת המעבר — ראו §10
  activated_at:  datetime
}
```

- **שולח:** `activated_by` (מנהל) או `null` + `note="national:<שם הגורם>"` (פיקוח).
- **סיבה:** שדה `note` — **חובה בכל מעבר** ("תרגיל מתוכנן", "אזעקות באזור", "חזרה לשגרה"). מפתח: ולידציה שהשדה לא ריק לפני שמירה.

> **אין מחיקת יומן.** הורדה משגרה → חירום → שגרה מייצרת שלוש רשומות. ההיסטוריה של "מתי היינו בחירום ולמה" היא נכס — לתחקור, לדוחות פיקוח, ולמחקר.

## 4. מה קורה טכנית ברגע ההחלפה

מעבר מצב הוא **אירוע אחד בשרת** שמפעיל שרשרת דטרמיניסטית. הסדר קובע.

```
[1] כתיבה          → INSERT SystemMode חדש (append-only). זה הרגע שבו המצב "השתנה".
[2] הטבעה קדימה    → כל אירוע חדש מרגע זה מטביע את ה-mode החדש. אירועים קיימים לא נוגעים.
[3] דחיפת התראה    → Notification(kind=mode_change) לכל הנוגעים (ראו §4.1). payload_ref → SystemMode.id.
[4] רענון לקוחות   → הלקוחות מגלים את המצב החדש (ראו §4.2) וטוענים MODE_CONFIG חדש.
[5] החלפת מסכי בית → check-in מתחלף presence↔emotional; דגלים נדלקים/כבים; צבע-מצב מתחלף.
[6] כיול דוחות     → תזמון הדוחות (cron) עובר לתדירות המצב החדש.
```

### 4.1 מי מקבל התראת מעבר (`Notification.kind=mode_change`)

| נמען | `recipient_kind` | תוכן |
|------|-------------------|------|
| כל תלמיד פעיל בבית הספר | `student` | "המצב השתנה — זה מה שקורה מחר" (שפה פשוטה, לפי המצב החדש) |
| הורה (דרך `guardian_phone`) | `parent` | עדכון מרגיע — רק במעבר ל-`remote`/`emergency` |
| כל איש צוות פעיל בבית הספר | `staff` | "בית הספר עבר ל-<מצב>. הלוח שלך מתעדכן" |

ההתראות נכנסות לתור (`status=queued`) ונשלחות דרך שכבת הרשת החלשה (חלק ג) — לא חוסמות את המעבר עצמו.

### 4.2 איך הלקוח מגלה שהמצב השתנה

הלקוח לא יכול להניח שהוא "מחובר". שלוש דרכי גילוי, לפי סדר עדיפות:

1. **בכל טעינת מסך** — הלקוח קורא `GET /api/mode?school_id=…` (תשובה זעירה: `{mode, since, is_drill}`). זו נקודת האמת. מטמון קצר של 60 שניות כדי לא להעמיס.
2. **בפתיחת ה-magic link** — המצב מוחזר יחד עם ה-session (חלק ב §6), כך שהמסך הראשון כבר נכון.
3. **התראת ה-push** (`mode_change`) — כשהתלמיד לוחץ עליה, ה-URL כולל את המצב החדש, והלקוח מרענן מיידית.

> **אין תלות ב-WebSocket.** רשת חלשה = לא סומכים על חיבור חי. Polling קליל בטעינת מסך + הטבעת מצב בקישור מספיקים. תלמיד שפותח את האפליקציה מקבל את המצב הנוכחי; תלמיד שלא פתח — יקבל אותו בפעם הבאה שיפתח, וזה בסדר (המצב לא "פועל" עליו כשהוא לא מסתכל).

### 4.3 החלפת מסך הבית — פירוט

- **check-in:** הלקוח קורא `MODE_CONFIG[mode].checkinType`. `presence` → מסך כפתור אחד ("אני כאן"). `emotional` → מסך 4 מצבי רוח. **אין שני קבצים** — אותו קומפוננטה, ענף לפי הקונפיג.
- **דגלים רגשיים:** `flagsActive` שולט אם `distress_flag` בכלל נכתב. בשגרה/מרחוק — check-in הוא `presence`, אין `mood`, אין דגל. חירום — `mood` נאסף, `distress_flag` נגזר, `FlagEvent` עשוי להידלק.
- **צבע-מצב:** משתנה CSS יחיד (`--mode-accent`) מתחלף לפי `accentColor`. כל הדף מחליף גוון בלי רה-לוד (עקבי עם `design-system.html`).
- **תדירות דוחות:** ה-cron של הדוח היומי למנהל (`Notification.kind=daily_report`) נדלק כש-`principalReport` דורש יומי, וכבה בשגרה. שינוי המצב מעדכן את רישום ה-cron לבית הספר.

## 5. מצב תרגולת — תרגיל ארצי

**"תרגולת" = תרגיל מעבר-מצב מתוכנן** (spec §6, פאזה 4: "תרגיל מעבר מצב פעמיים בשנה, כמו תרגיל רעידת אדמה"). מבחינת התלמיד והמורה הוא **נראה בדיוק כמו חירום** — אותו check-in רגשי, אותו לוח דופק, אותם דוחות — כדי שהאימון יהיה אמיתי. אבל הוא **מסומן**, ו**לא מזהם את הנתונים הרגשיים**.

### 5.1 ייצוג טכני

```
SystemMode {
  mode:     "emergency",   // התנהגות זהה לחירום — האימון חייב להיות אמיתי
  is_drill: true,          // ✎ שדה חדש — ראו §10
  note:     "תרגיל ארצי <תאריך>",
  activated_by: null       // ארצי
}
```

`is_drill` **מוטבע קדימה** על כל אירוע שנוצר בזמן התרגיל, בדיוק כמו `mode` (`CheckIn.is_drill`, `Assignment.is_drill` וכו' — ✎ §10).

### 5.2 מה שונה בתרגולת מחירום אמיתי

| היבט | חירום אמיתי | תרגולת |
|------|--------------|---------|
| מסכי התלמיד/מחנך | מלא | **זהה** — האימון אמיתי |
| `CheckIn.mood` (תוכן רגשי) | נשמר 30 יום | **לא נשמר בכלל** — נכתב ל-`mood=null` או נמחק מיד בסוף התרגיל |
| `FlagEvent` (הדלקת דגל) | נדלק, נשמר לשנה | **לא נדלק** — תרגיל לא מייצר היסטוריית דגלים |
| דוחות מנהל/פיקוח | אמיתיים | נשלחים אך **מסומנים "תרגיל"** בכותרת ההודעה |
| מדדים מצרפיים | נספרים | נספרים בנפרד, מסומנים `is_drill` — לא מזהמים מגמות אמת |
| הורים | עדכון אמיתי | הודעה שמסמנת "תרגיל מתוכנן" (בלי להבהיל) |
| מחיקה בסיום | לפי לוח זמנים רגיל | **פורג מיידי** של כל תוכן רגשי בסיום התרגיל |

### 5.3 כלל הזהב של התרגולת

> **תרגיל לא מייצר נתון רגיש קבוע.** התלמיד מתאמן ללחוץ "קשה לי", המחנך מתאמן לראות דגל ולפנות — אבל אף אילוץ רגשי אמיתי לא נכתב לאחסון. בסיום התרגיל, שאילתת פורג מוחקת כל `CheckIn` עם `is_drill=true` (לרבות `mood`), ואף `FlagEvent` לא נוצר מלכתחילה. הנוכחות המצרפית ("כמה השתתפו בתרגיל") נשמרת מסומנת, כי היא לא רגישה ומשמשת להערכת המוכנות.

# חלק ב — כניסה בשתי שכבות

## 6. שכבת הקשר — magic link (הליבה, אפס חיכוך)

זו שכבת החיים. היא **חייבת** לעבוד בלחיצה אחת, בלי סיסמה, בחירום, ברשת חלשה. כל החלטת עיצוב כאן כפופה לעיקרון: **הקישור האישי הוא קו החיים — הוא לא נשבר.**

### 6.1 הנפקה

- לכל `Student` יש `access_token` — **מחרוזת אקראית אטומה**, 22 תווים base62 (~128 ביט אנטרופיה). לא מכיל מידע על התלמיד (לא ת"ז, לא שם).
- הקישור: `https://<domain>/s/<access_token>` (`/s/` = student). עובד ב-WhatsApp, ב-SMS, ובכל דפדפן — הוא URL רגיל.
- מונפק **פעם אחת** בעת יצירת התלמיד במצבת, ונשלח דרך `Notification(kind=personal_link)` לטלפון התלמיד (`Student.phone`).
- **אותו קישור לתמיד.** התלמיד שומר אותו (מצמיד בוואטסאפ). זה "הקישור שלי". אנחנו לא מבקשים ממנו כלום כדי להיכנס — הוא לוחץ ורואה את "היום שלי".

### 6.2 תוקף — למה אין תפוגה קשיחה

magic link קלאסי פג אחרי דקות. **כאן זה היה הורג את העיקרון:** בחירום, בשלוש בלילה, אחרי אזעקה, אסור שהקישור "פג". לכן:

- **`access_token` לא פג בזמן.** הוא חי כל עוד התלמיד פעיל במצבת. אין "לחץ כאן לקבל קישור חדש" — זה חיכוך שאסור לנו.
- **ההגנה היא לא תפוגה — היא היקף.** מה שהקישור פותח הוא **שכבת הקשר בלבד** (check-in, משימת היום, "המורה ראה", רצף). זו שכבה בסיכון נמוך: אין בה תוכן רגיש של אחרים, אין גישת מחנך/מנהל, ואי אפשר להזיק דרכה (ראו §9). לכן קישור אטום ויציב הוא סיכון מקובל — התועלת (קו חיים שלא נשבר) עולה על הסיכון.

### 6.3 חידוש שקוף (rotation) — בלי שהתלמיד ירגיש

אנחנו כן רוצים יכולת להחליף טוקן (אם דלף, אם המכשיר אבד). הפתרון: **רוטציה שקופה** שלא מפילה את הקישור הישן פתאום.

1. בפתיחה ראשונה של הקישור במכשיר, השרת מנפיק **session למכשיר** — עוגייה חתומה (`httpOnly`, `Secure`, `SameSite=Lax`) או רשומת session ב-localStorage, עם תוקף מתגלגל של 45 יום שמתחדש בכל כניסה. מהרגע הזה, המכשיר "זכור" — התלמיד לא צריך את הקישור המקורי שוב.
2. **הטוקן עצמו יכול להתחלף ברקע** בלי שהתלמיד ידע: כשמנפיקים `access_token` חדש (יזום — מספר התחלף/אובדן), השרת שומר את הישן ב**חלון חסד של 14 יום** שבו הוא עדיין תקף ומבצע redirect ל-session הפעיל. הקישור החדש נשלח בוואטסאפ ומחליף בהדרגה.
3. אחרי חלון החסד — הטוקן הישן מושבת (`410 Gone` → מסך "בקש קישור מהמחנך", לא שגיאה מפחידה).

```
פתיחת /s/<token>:
  token תקף?  ──לא──►  410: "הקישור הזה כבר לא פעיל. פנה/י למחנך/ת לקישור חדש."
     │כן
     ▼
  session קיים במכשיר?  ──כן──►  טען את "היום שלי" של אותו student. חדש את ה-session (45 יום).
     │לא
     ▼
  צור session חדש למכשיר (מקושר ל-student_id של הטוקן). טען "היום שלי".
```

> **אין OTP, אין קוד SMS, אין סיסמה בשכבת הקשר.** כל שכבת אימות נוספת כאן = חיכוך שסותר את עיקרון 4. האימות הוא **החזקת הקישור** — כמו מפתח לבית.

## 7. שכבת הלמידה — הרשמה קלה (`Student.registered`)

שכבת הלמידה (תרגולים, מופעי הערכה **עם ציון**) דורשת תיעוד לאורך זמן — כדי שהציון של תלמיד ייקשר אליו לאורך חודשים, וכדי שתוצריו לא יתערבבו עם אח שמשתמש באותו טלפון. לכן היא דורשת **הרשמה חד-פעמית קלה**. אבל — **ההרשמה לעולם לא חוסמת את הקשר.**

### 7.1 מה נאסף — מינימום מזהה

ההרשמה אוספת את **המינימום המוחלט** לקשירת תוצרים לאורך זמן, בהתאם לתיקון 13:

| נאסף | למה | הערה |
|------|------|------|
| אישור שם פרטי | לוודא שזה התלמיד הנכון על המכשיר | כבר קיים ב-`Student.first_name` — רק אישור |
| קוד אישי 4 ספרות (PIN) | להגן על הציונים במכשיר משותף (§8) | נשמר **hashed** בלבד; לא סיסמה, לא מזהה |
| `registered = true` | דגל שהתלמיד בשכבת הלמידה | ברירת מחדל `false` |

**לא נאסף:** ת"ז, אימייל, כתובת, שם משפחה, תמונה. שום דבר מעבר לזה. הקוד האישי הוא **נוחות והגנה במכשיר משותף**, לא אימות זהות מול המדינה.

### 7.2 מתי — עצל (lazy), רק כשצריך

ההרשמה **לא** קופצת בכניסה, לא בצ'ק-אין, ולא ביום הראשון. היא מופיעה **רק ברגע שהתלמיד לראשונה מתחיל מופע הערכה שנושא ציון** (`ContentUnit.unit_type=assessment`):

```
תלמיד לוחץ "התחל" על מופע הערכה:
   registered == true?  ──כן──►  ישר לתרגול
      │לא
      ▼
   מסך הרשמה קל (מסך אחד): "כדי לשמור לך את הציונים, בוא נסמן שזה אתה."
   [אישור שם] [בחר קוד 4 ספרות]  ──►  registered=true  ──►  ממשיך לתרגול
      │
      └── כפתור "אחר כך" תמיד קיים ──►  חוזר, בלי ציון שמור (אפשר לתרגל בלי לשמור)
```

- משימת **קשר** רגילה (`unit_type=task`) — **לא דורשת הרשמה כלל**. תלמיד לא רשום עושה check-in, פותח משימת 10 דקות, לוחץ "סיימתי", ומקבל "המורה ראה". הכל בלי הרשמה.
- רק **ציון** דורש הרשמה, כי ציון בלי זהות יציבה הוא חסר ערך.

### 7.3 איך ההרשמה לא פוגעת בכניסת החירום

זה הכלל האדום של החלק הזה:

> **מסלול הקשר לעולם לא עובר דרך מסלול ההרשמה.** בקוד: פונקציית הכניסה (§6.3) מובילה ישר ל-"היום שלי" ול-check-in — היא **אף פעם** לא בודקת `registered`. הבדיקה של `registered` חיה **רק** בתוך זרימת מופע ההערכה (§7.2). תלמיד במצוקה שלוחץ על הקישור שלו ב-2 בלילה רואה את מסך ה-check-in הרגשי מיד, בלי שום מסך ביניים.

בדיקת קבלה למפתח: *נתק את שרת ההרשמה לגמרי. האם check-in עדיין עובד?* חייב להיות **כן**.

## 8. תרחישי קצה — כל אחד סגור

### 8.1 החלפת מספר טלפון

התלמיד קיבל מספר חדש.

1. איש צוות (מחנך/מזכירות) מעדכן `Student.phone` למספר החדש.
2. השרת מנפיק `access_token` חדש, שולח קישור חדש למספר החדש (`Notification kind=personal_link`), ומכניס את הטוקן הישן ל**חלון חסד 14 יום** (§6.3).
3. ה-session במכשיר הישן (אם זה אותו מכשיר) **ממשיך לעבוד** — החלפת מספר ≠ החלפת מכשיר. אין נעילה החוצה.
4. אחרי 14 יום — הטוקן הישן מושבת.

### 8.2 אובדן טלפון

הטלפון אבד/נגנב. הטוקן על מכשיר לא-מהימן.

1. איש צוות מפעיל **"בטל והנפק מחדש"** (`revoke & reissue`) על התלמיד.
2. הטוקן הישן מושבת **מיידית** (בלי חלון חסד — זה המקרה שבו חלון חסד מסוכן), וכל ה-sessions הפעילים שלו נפסלים.
3. טוקן חדש + קישור חדש נשלחים למספר החלופי (טלפון הורה / מכשיר חדש).
4. **מה שהיה חשוף במכשיר האבוד:** רק שכבת הקשר (check-in, משימת היום) — סיכון נמוך. הציונים מוגנים ב-PIN (§7.1). מסכי מחנך/מנהל **לא נגישים בכלל** מטוקן תלמיד (§9). אין תוכן רגיש של תלמידים אחרים.

### 8.3 אח קטן עם הטלפון (שימוש לא-מכוון)

אח צעיר משחק עם הטלפון ופותח את האפליקציה.

- **check-in:** סיכון נמוך — לכל היותר check-in כוזב. הוא **אידמפוטנטי ליום** (§11.3): check-in שני באותו יום לא סופר פעמיים ולא משנה סטטוס. אם נלחץ "קשה לי" בטעות — המחנך רואה אדם, פונה, ומגלה. זה נסבל: עדיף false-positive שמוביל לשיחה מאשר להחמיץ מצוקה אמיתית.
- **ציונים:** מוגנים — מופע הערכה דורש PIN (§7.1) לפני שהוא נכתב לתלמיד. אח בלי הקוד לא יכול "לזייף" ציון.
- **מסכי צוות:** לא נגישים — טוקן תלמיד לא פותח שום מסך רגיש.

### 8.4 מכשיר משפחתי משותף (נפוץ מאוד!)

כמה אחים/תלמידים חולקים טלפון אחד. **התרחיש הכי שכיח בקהל היעד.**

- **לכל תלמיד קישור אישי משלו.** המכשיר יכול להחזיק **כמה sessions במקביל** (רשימת `student_id` זכורים ב-localStorage).
- בפתיחת האפליקציה, אם יש יותר מ-session אחד במכשיר — **מסך "מי אתה?"** מציג את התלמידים הזכורים (שם פרטי + אווטאר-אות). לחיצה בוחרת session. פתיחת קישור אישי חדש מוסיפה session לרשימה.
- **אין דליפה בין אחים:** כל session תחום ל-`student_id` של הטוקן שלו. אח א' לא רואה את משימות אח ב'.
- **ציונים בין אחים:** ה-PIN (§7.1) מונע מאח לראות/לשנות ציון של אחר. שכבת הקשר משותפת ופתוחה (סיכון נמוך); שכבת הציון מופרדת ב-PIN.

```
פתיחת האפליקציה במכשיר:
   כמה sessions?
     0  ──►  צריך קישור אישי (פתח /s/<token>)
     1  ──►  ישר ל-"היום שלי" של אותו student
     2+ ──►  מסך "מי אתה?" → בחירת student → "היום שלי"
```

### 8.5 טבלת סיכום תרחישי הקצה

| תרחיש | פעולה | טוקן ישן | סיכון | מוגן ע"י |
|--------|--------|-----------|--------|-----------|
| מספר התחלף | update phone + reissue | חלון חסד 14 יום | נמוך | חלון חסד, session שורד |
| טלפון אבד | revoke & reissue | מושבת **מיידית** | בינוני | ביטול מיידי + PIN + היקף מוגבל |
| אח קטן | — | — | נמוך | check-in אידמפוטנטי + PIN לציון |
| מכשיר משותף | multi-session | — | נמוך | session per token + מסך "מי אתה?" + PIN |

## 9. שכבה נוספת — מסכי מחנך / מנהל (נתונים רגישים)

טוקן תלמיד פותח שכבת קשר בסיכון נמוך. מסכי הצוות מחזיקים **נתונים רגישים** — רשימת אדומים, דגלים רגשיים, הערות מחנך. הם דורשים **שכבת הגנה נוספת**.

| היבט | טוקן תלמיד (`/s/`) | טוקן צוות (`/t/`) |
|------|---------------------|---------------------|
| כניסה | קישור בלבד, בלי סיסמה | קישור **+ שכבה שנייה** (ראו למטה) |
| מה נגיש | "היום שלי" בלבד | לוח דופק, אדומים, דגלים, הערות — לפי `StaffRole` |
| session | 45 יום מתגלגל | קצר יותר; פעולות רגישות דורשות אימות מחדש |
| נתוני תלמידים אחרים | **אין גישה כלל** | לפי היקף התפקיד בלבד |

**השכבה השנייה של הצוות:**

1. **קוד אישי (PIN) בקישור הראשון במכשיר.** בפתיחה ראשונה של `/t/<token>` איש הצוות קובע PIN. כל כניסה עוקבת מאותו מכשיר דורשת PIN (או ביומטריה של המכשיר). זה מגן על נתוני קטינים אם הטלפון של המורה נפתח.
2. **הרשאה נגזרת מ-`StaffRole`, לא מהטוקן.** הטוקן מזהה *מי* איש הצוות; מה שהוא רואה נקבע מ**איחוד ההרשאות** של שורות ה-`StaffRole` הפעילות שלו (`data-model` §3). מחנך רואה את כיתתו; יועצת רואה דפוס חוצה-כיתות מ-`FlagEvent`; מנהל רואה אגרגט; פיקוח רואה מצרף בלי שמות. **ההפרדה נאכפת בשאילתה, לא בממשק.**
3. **פעולות רגישות דורשות אימות מחדש.** צפייה ב-`FlagEvent` / הערת מחנך / רשימת אדומים מלאה — דורשת PIN טרי אם ה-session ישן מ-X דקות. (בניגוד ל-check-in של תלמיד, שאסור שידרוש כלום.)

> **קו אדום מבני:** אין נתיב שאילתה שמחזיר נתון רגיש של תלמיד לטוקן תלמיד, ואין נתיב שמחזיר שם תלמיד לרמת הפיקוח (`data-model` §0.3). ההפרדה היא בקוד השאילתה — לא בהסתרת כפתור ב-UI.

# חלק ג — עבודה ברשת חלשה

עיקרון 6: קובץ HTML אחד קל, בלי ספריות כבדות, נבדק ב-3G. הכניסה וה-check-in **חייבים** לעבוד כשהרשת גרועה או נופלת — זה בדיוק מצב החירום.

## 10. אסטרטגיית טעינה

- **App shell סטטי.** ה-HTML+CSS+JS של המסגרת (check-in, "היום שלי") נטענים פעם אחת ונשמרים ב-Service Worker cache. פתיחות הבאות = טעינה מהמטמון, מיידית, גם אופליין.
- **בלי ספריות כבדות.** אין React/framework בצד התלמיד. Vanilla JS, CSS inline קריטי. יעד: מסך ה-check-in אינטראקטיבי מתחת ל-2 שניות ב-3G.
- **נתונים אחרי מסגרת.** ה-shell עולה ראשון (מיידי), ואז הנתונים הקטנים (`/api/mode`, משימת היום) זורמים מעל. התלמיד רואה את המסך שלו לפני שהנתונים הגיעו — עם placeholders, לא מסך לבן.
- **תמונות/קבצים של המורה מוקלים.** `Attachment` כבד מומר לגרסה קלה (§`data-model` 2.11) — מה שמגיע לתלמיד עובד ברשת חלשה, לא נחסם.

## 11. מה נשמר מקומית (offline-first לקשר)

| נשמר מקומית | איפה | למה |
|--------------|------|-----|
| App shell | SW cache | פתיחה מיידית ואופליין |
| מצב נוכחי (`mode`, `is_drill`) | localStorage (TTL 60ש') | המסך הנכון גם לפני שהרשת ענתה |
| משימת היום (`Assignment` + `ContentUnit.body`) | localStorage / IndexedDB | לתרגל 10 דקות בלי רשת |
| רצף אישי | localStorage | תצוגה מיידית, מסתנכרן ברקע |
| sessions של המכשיר (§8.4) | localStorage | מסך "מי אתה?", בחירת תלמיד |
| **תור check-in ממתין** | localStorage | ראו §11.2 |

**לא נשמר מקומית:** תוכן רגשי של אחרים, מסכי מחנך/מנהל, ציונים של אחרים — שום דבר רגיש לא יורד למכשיר התלמיד.

### 11.2 check-in נשלח בלי רשת — תור מקומי

זה התרחיש הקריטי: תלמיד עושה check-in בחירום, והרשת נופלת. **אסור שהלחיצה תיעלם.**

```
תלמיד לוחץ check-in:
   [1] כתוב מיד ל-outbox המקומי (localStorage): {student_id, day, type, mood?, idempotency_key, ts}
   [2] UI אופטימי: "נשמר. יישלח כשתהיה רשת." (לא "נשלח" — ראו קו אדום למטה)
   [3] נסה לשלוח עכשיו:
         הצליח?  ──►  הסר מה-outbox. הצג סטטוס אמיתי.
         נכשל?   ──►  נשאר ב-outbox. Background Sync ינסה שוב בכל חיבור/פתיחה.
   [4] בחיבור מחדש: flush ל-outbox בסדר כרונולוגי.
```

### 11.3 אידמפוטנטיות — בלי כפילויות

- כל check-in נושא `idempotency_key = hash(student_id + day + type)`. אם ה-flush שולח את אותו check-in פעמיים (רשת מהבהבת), השרת מזהה את המפתח ולא סופר פעמיים. זה גם מה שהופך check-in כפול (אח קטן, §8.3) ל**בטוח**.
- הכלל: **check-in אחד לתלמיד ליום לכל `type`.** שליחה חוזרת מעדכנת, לא מכפילה.

### 11.4 קו אדום — "המורה ראה" לא מזויף אופליין

> חיווי **"המורה ראה אותך"** מבוסס על `CheckIn.seen_by` — **אישור אנושי אמיתי** של מחנך (`data-model` §2.7; `copy-student` T1.3). אסור להציג אותו אופליין או על סמך הנחה. אופליין, ה-check-in מציג **"נשמר, יישלח כשתהיה רשת"** — ולא מבטיח שמישהו ראה. החיווי "המורה ראה" מופיע **רק** אחרי שני תנאים: (א) ה-check-in הגיע לשרת בפועל, ו-(ב) מחנך לחץ "ראיתי". אנחנו לא משקרים לילד בחירום שראו אותו כשאף אחד עוד לא ראה.

## 13. שדות חדשים שהמסמך מניח (✎ דורש עדכון data-model / החלטת מיטל)

המסמך נשען בעיקר על ישויות קיימות. הפריטים הבאים **נדרשים למימוש** ואינם עדיין ב-`data-model.md` v1.2:

1. **`SystemMode.note` כשדה חובה** — כבר קיים כ-`note` אופציונלי; המסמך דורש שיהיה **חובה** בכל מעבר (§3). החלטה: לאכוף ולידציה.
2. **`SystemMode.is_drill` (bool)** — לסימון תרגולת (§5). מוטבע קדימה על אירועים.
3. **`CheckIn.is_drill` (bool)** ואולי `Assignment.is_drill` — הטבעת התרגיל על אירועים, לצורך פורג ובידוד מדדים (§5.1).
4. **`Student.pin_hash` (string?)** — קוד אישי מוצפן לשכבת הלמידה/מכשיר משותף (§7.1). מזעור: hash בלבד, לא PIN גולמי.
5. **`StaffMember.pin_hash` (string?)** — השכבה השנייה של מסכי הצוות (§9).
6. **מנגנון session/רוטציה** — טבלת `DeviceSession` קלה (`token`, `subject_id`, `subject_kind`, `expires_at`) או עוגייה חתומה ללא-state. החלטת ארכיטקטורה (§6.3). לא חושף מידע אישי.

> אלה **תוספות תשתית**, לא שינוי מודל מהותי. הן לא נוגעות בעקרון אפס-השכפול ולא בהפרדת הגישה. מומלץ להטמיע ב-`data-model` v1.3 יחד עם החלטת מיטל על אכיפת `note` חובה ועל שמירת PIN.
